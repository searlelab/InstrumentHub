# User Stories for InstrumentHub

### User Stories:

**A new lab member wants to run their first experiment:** As a new lab member, I want the scheduler to guide me through the lab’s usage rules when I book time, so I can request instrument access without accidentally violating PI allotments, project limits, or fairness expectations. My goal is to spend my time planning experiments, not interpreting lab policy documents, so the scheduler should make the rules visible, predictable, and easy to act on while still enforcing the rules. In the ideal workflow, I do not want to discover policy problems only after filling out an entire request. Instead, once I choose a PI and project, I want the system to show me relevant constraints in plain language, such as how much time remains for that PI, what is the maximum number of consecutive days I can use for the project, and whether the requested reservation would exceed either limit. I expect the system to automatically calculate those rules based on the dates and daily times I selected, and to clearly explain why a reservation can or cannot proceed. If my request is acceptable, I want it confirmed without any extra work. If it exceeds a project or PI limit, I want the system to stop me early and provide a direct path to request additional time, ideally carrying forward the reservation details I already entered so I do not have to repeat them.

**A lab member who wants to identify and contact the current instrument user during an interruption (like the power going out):** As a lab member, I want the scheduler to show me the contact information of the person currently using an instrument if something urgent happens, like a power outage, so that I can reach them immediately and minimize the risk of data loss or instrument problems. The goal in this situation would be to avoid wasting time searching through external records or directories for this information. In the ideal workflow, the scheduler should maintain a backend user directory that is updated whenever a new user is added to the system, including their contact details like their phone number and email address. When I view the calendar and find the current booking for an instrument, I want to be able to hover over the scheduled user’s name and immediately see their contact information tied to that time slot. I expect the system to show the contact details for the correct user based on the current date and time, and to keep that information accurate as the user list changes. If no one is currently scheduled on the instrument, I want the calendar to clearly indicate that there is no active user so that I do not try to contact the wrong person.

**A lab member who wants to see who’s coming up in the schedule:** I am a lab member who is curious to know how far out the instrument is booked so that I can schedule my experiment. I want the scheduler to show me a calendar that shows when the instrument is booked, with basic information (such as instrument handler initials) attached to that booking. I would like the calendar bookings to be color coded, where maintenance booking is red, and each lab member has a personalizable color for their reserved time blocks. If I click on the booking, I would like it to pull up the booking main page that contains all of the details of the project run time. This main page should include things like duration, column setup, project number, and instrument handler. This will help me understand what will have just run on the instrument, for how long, and be able to anticipate startup time for my own experiment. As a lab member, I have access to view the calendar and to book my own experiments, but I cannot double book or change something already booked if I am not the instrument handler for that experiment. This should require a password or code prompt to ensure other lab members are not changing booked experiments or accidentally double booking. Additionally, I would like the schedule to notify lab members when the instrument is free, particularly if there is a cancellation, since running the instrument at capacity is important.

**An experienced lab member who wants to schedule a new experiment quickly and without hassle:** As a lab member with mass spectrometry experience (I have gone through training for the instrument), I want to quickly view and place a scheduling request. I want a wizard that lets me either view the schedule or find the earliest available date for the instrument. To do so, I want the wizard to request certain information that will be used to schedule the event up front, such as how much time is needed, an experiment name or code to use as the title on the calendar, and the user. Additionally, the wizard could try to obtain information that is not essential to scheduling, such as the material, a description of the experiment, specific gradient lengths, whether libraries are present, and any notes to communicate to the scheduling committee. Once this intake is complete, the scheduler should record the date and time that the intake was received and save the responses so that humans can ultimately decide on the schedule. On Fridays, the scheduling committee will convene to review the schedule and intakes from previous weeks that have not yet been scheduled. Humans need to be able to view the calendar and approve new experiment requests or modify existing ones. I need to be able to move or extend current experiments. To assist humans with scheduling, the scheduler should request either the expected duration or the number of samples from the user. If the user provides the number of injections, the Scheduler should be able to estimate how long the experiment would take. This can be done by multiplying the number of injections by the gradient length (\~40 minutes per injection) and adding two QC injections (each around 20 minutes) for every 8 hours of samples. The scheduler can suggest the best time to schedule the experiment to the scheduling committee. Between experiments, the scheduler should allocate a day of flexible time for maintenance and calibration. 

- A user cannot schedule for more than a week without approval from an admin/PI.   
- Build in a notion of the type of sample that’s run. For example, if we schedule a large liver experiment, we do not want to schedule a large single-cell experiment immediately afterward. 

**A lab member who wants to know when their previously scheduled experiment is actually in the schedule:** As a lab member, I want to clearly see where my experiment was successfully placed on the instrument calendar after I submit a reservation, so that I know my time is secured and I can plan my experiment. My goal is to avoid uncertainty about whether my scheduling request was actually saved or if it failed due to a conflict or rule violation. In this case, once I confirm a scheduled experiment, the system should immediately display my reservation in the calendar at the correct date and time, along with my name, contact and project details. The scheduler should provide immediate visual confirmation, such as rendering the time block on the calendar and displaying a confirmation message. I expect the system to ensure that the displayed booking reflects exactly what I requested, including start and end times, and that it persists when I refresh or revisit the page. If the booking was not successfully created, I want the system to clearly indicate that it failed and explain why, so I can correct the issue.

**Two lab members try to schedule at the same time:** Two people interested in scheduling the instrument attempt to book time for an experiment at the same time. In this case, the “same time” means that these two people were filling out the booking request form at the same time, for an overlapping period of time, but one person finishes the form before the other person. To avoid the instrument being double-booked, the request form should immediately prompt which days/time you are requesting to book the instrument. This should freeze this time so that no one else can edit or request to book this time (similar to how it would be if the time was formally booked). These dates cannot be edited once you have started filling out the form. An ideal application will autorefresh this every time someone starts a form. “Officially” booked time should appear different on the calendar than “requested” booked time. Requested time should be screened by a senior-level administrator for the application, which will be a second-level check that the instrument is not double-booked. If a person attempts to book time at the same time as another person, they will receive an “error” message that indicates the instrument is already booked at that time, and to select alternative dates. Locks should be added quickly so that other users know that the time is potentially locked. Ideally, this should work like concert tickets where the time gets released after a certain time.

**A lab member whose experiment is displaced by emergency maintenance:** As a lab member with a scheduled experiment, I want to understand how emergency maintenance affects my reservation, so that I can adjust sample preparation, staffing, and downstream plans. If my experiment is paused, shifted, or placed into an unknown restart state, I want the scheduler to show the current status clearly and explain what is known. I need to know whether my experiment is still in the same relative order, whether its duration is preserved, whether I need to take action, and when I should expect another update. The story is successful if affected users receive timely, non-duplicative notifications and can open the calendar to see the same status that the administrator sees.

\-A lab member who wants to know how much time to schedule for their experiment  
\-A lab member who needs to use the laboratory computer to process data (SEPARATE from active experiment)  
\-A lab member who needs to use the laboratory computer (while ACTIVELY running samples on the instrument or immediately AFTER running samples)  
\-Two instruments – needs to be included in previous stories (able to select preferred instrument, separate queues?, etc)

**An administrator who needs to schedule routine instrument maintenance:** As the instrument administrator, I need to block off time for routine maintenance at regular intervals and on an as-needed basis. For routine maintenance, I would like to have the ability to block off time on the calendar and assign smaller maintenance tasks to users. Specifically, I’d like to assign tasks that need to be done weekly, such as calibrating, changing the ion transfer tube, switching solvents, running the purge pump, and cleaning the needle seat scripts before certain experiments. Each weekly task typically takes 1 hour to complete, except for calibrating, which takes 2-4 hours. There is also longer maintenance that is done less regularly that we will want the Scheduler to consider, such as cleaning the ion optics, which is done every 2-3 months. An ideal app would automatically recommend when maintenance is due, let users mark when they’ve completed maintenance, and let them adjust the frequency or number of regular maintenance tasks. 

**An administrator who needs to schedule emergency instrument maintenance:** If emergency maintenance is needed (for example, the ion optics need to be cleaned due to contamination), 1 day into a 5-day experiment for a user, I have to be able to pause the current experiment, modify the calendar to account for instrument downtime, and notify other users of the schedule change. When modifying the schedule after emergency maintenance, we will want to keep everything on the schedule consistent, especially the placement of scheduled routine maintenance events and the length of time each experiment is reserved, while shifting the schedule forward in time by 24-hour increments. Simple maintenance, such as changing solvents, typically takes 1 day but may take multiple days if a bakeout is needed. As a result, when emergency maintenance is necessary, I need to inform the Scheduler, tell it how long the maintenance will last, and approve the modified calendar before lab members are notified. Once emergency maintenance begins, I may need to shift the schedule multiple times. As a result, I want to immediately notify lab members whose experiments begin next week, then notify other users after the emergency maintenance event has concluded. On the calendar, routine and emergency maintenance should be available for anyone who can access the schedule to view, and allow edit access to other admins/PIs. 

**An administrator who needs to pause the schedule during an unresolved instrument outage:** As an instrument administrator, I want to pause an instrument schedule when the duration of an outage is unknown, so that existing experiment order and reservation details are preserved while start and end dates remain uncertain. Emergency maintenance continues indefinitely if an instrument requires a Thermo service engineer to assess the issue on-site. In that case, I want the ability to “pause” the schedule. When pausing the schedule, I need the information for each experiment and the order of experiments to remain the same, but the start and end dates for each experiment will be unknown. The calendar should reflect this information, and the scheduler should not repeatedly notify users that their experiments are postponed during this time period. An instrument admin will inform the Scheduler of when the calendar will resume, but should be able to modify this time at any point. When I pause the schedule, I want the calendar to clearly show that the instrument is unavailable and that future events are pending rather than canceled. The system should keep each experiment’s project, user, PI, grant, duration, notes, and relative order intact, but should avoid repeatedly notifying users every time the outage remains unresolved. Once I know when the instrument can resume, I want to enter a restart date and preview a reconstructed schedule before sending updates. The story is successful if the schedule can enter an unresolved outage state, preserve future reservations, suppress excessive notifications, and resume only after an administrator approves the revised calendar.

**A PI who wants to build reports for an NIH RPPR for a specific grant:** As a PI preparing an NIH Research Performance Progress Report for a specific grant, I want to generate a usage report filtered by grant number, so that I can summarize how instrument time supported that funded project during the reporting period. In the ideal workflow, I select the grant, reporting date range, instrument or instruments, and optional filters such as PI, project, user, or experiment type. The scheduler should then produce a report showing reserved time, completed time, canceled time, users, PIs, project identifiers, experiment names, and relevant notes tied to that grant. I want the report to distinguish confirmed usage from requested, canceled, maintenance, and downtime blocks, because only some of those categories reflect actual grant-supported instrument use. The story is successful if I can export a clean summary table and visual report that traces every included hour back to specific calendar reservations and excludes unrelated instrument time.

**A PI who receives a complaint that one lab member is monopolizing the instrument:** As a PI, I want to investigate whether lab member X is monopolizing an instrument, so that I can respond fairly using schedule data rather than anecdotal impressions. In the ideal workflow, I search for a user and instrument over a defined time window, then see that person’s reserved hours, completed hours, canceled hours, number of reservations, average reservation length, consecutive days booked, and share of total instrument capacity. I also want to compare that usage against PI allotments, project limits, other users, and the lab’s fairness rules. The scheduler should highlight patterns that may indicate monopolization, such as unusually long consecutive reservations, repeated prime-time bookings, frequent extensions, or usage that crowds out other PIs. The story is successful if I can quickly determine whether the complaint is supported by the schedule data, identify the relevant reservations, and decide whether to adjust allotments, deny future extensions, or discuss scheduling behavior with the user and PI. All actions in the scheduler should be auditable to identify misuse.

**A PI who wants to understand how their lab is using its instrument allotment:** As a PI, I want to view my lab’s instrument usage and remaining allotment, so that I can manage my group’s experiments before users run into scheduling limits. I want to see total time used, time currently reserved, time pending approval, time canceled, and time remaining for each project and grant associated with my lab. The scheduler should make it easy to identify which lab members are using the most time and which projects are approaching their limits. If a user requests more time, I want to see the request in context, including the project, grant, experiment description, requested dates, and how approval would affect the lab’s remaining allocation. The story is successful if a PI can make informed approval decisions without having to ask an administrator to manually compile usage data.
